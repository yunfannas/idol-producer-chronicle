## 0. 产品目标与设计边界

这是 FM 风格的日本女性偶像制作人经营游戏。玩家是 **Producer**，不是 CFO、收银员或日常排班员。

**不变原则**：

1. **页面是信息空间，会议是决策空间**。Inbox 是核心工作台；六大经营模块仍为 Making / Training / Live / Audition / Finance / Policy。
2. **模拟系统与剧情独立**：历史 Scenario 通过人物、世界事件、公司决议、商业机会约束自由度，不修改基础 Attr / Trait / Palette / Performance / Fan / Economy 规则。
3. **一日为默认最小推进单位**，可连续逐日结算至七天或下一个重要事件；阻塞事项停下。避免逐小时微操。
4. **高频事务自动执行，低频关键决策由 Producer 负责**；允许 Attend / Delegate。委托 Staff 不等于不作为。
5. **每场 Live 保存完整可审计数据**，日常只显示事实和经营结算；演出技术表现主要在 Weekly Review 中以文字表达。
6. **人物有独立意志**，重要人生节点不会无限接受挽留；不靠任意数值罚分制造悲剧。
7. 故事模式极少 Bad End。章节结束时如有合理重组路径，允许公司干预、招聘、融资等有代价、有记录的补救继续故事。
8. **无需给 1st One-man 和 TIF 单独开发 UI**。它们通过统一 Live 页面和事件、外部评论获得特殊意义。

## 0.1 L2 / L3 / Runtime 权威数据边界（v0.2 新增）

- **L1**：可追溯的现实成员、团体、歌曲、演出、场馆和时间事实，不把推断写为原始事实。
- **L2B**：从冻结或版本化的歌曲语义证据推导 Song Palette；再按本地歌曲权重推导完整曲库的 Group Catalog Palette。推断的模型、证据、置信度与 review 状态必须保留。**合并到 main 不等于所有歌曲已经人工通过审核**。
- **L3**：根据剧本开局时间切断未来信息，按当时成员／歌曲／组织状态生成 Scenario Team Palette 与其他开档状态；不可直接将全历史 Group Catalog Palette 倒灌到 2013 年开局。
- **Runtime**：成员训练、曲目编排、Performance、粉丝与经济逐日／逐周运行。计算结果可以真实存在但受 Producer Knowledge 控制，不将 L2 的分类器置信度作为游戏内技能或演出评分。
- **仓库职责**：`idol-data-lab` 维护研究库和审核后导出；`idol-producer-web` 消费显式同步的游戏用数据。版本核对不代表已同步或已运行测试。

**游玩时长目标（序章）**：快速约 60 分钟，标准约 120 分钟，深度游玩可能超过 3 小时；这是测试目标，不是时间锁。

## 1. UI 信息架构（mobile-first）

### 1.1 全局导航

移动端四个常驻底部入口：

| 入口 | 内容 | 典型流程 |
| --- | --- | --- |
| **Inbox**（首页） | Blocking、提案、成员请求、Weekly Review、Live 结算、剧情 | Inbox → Detail → Attend/Delegate/Approve → 返回 |
| **Calendar** | 每日/未来日程、邀请、出演冲突与时间推进 | Calendar → Event → Detail |
| **Members** | 团体与人物列表、角色卡、能力/关系/履历、主动交流 | Members → Character → Topic / Meeting |
| **Manage** | Making、Training、Live、Audition、Finance、Policy | Manage → 模块 → 对应专题会议 |

桌面端采用同数据、同页面语义的自适应布局：左侧导航＋Inbox 列表＋右侧详情；复杂报表可横向扩展。不要分别开发两套产品逻辑。

### 1.2 Inbox 信息层级

1. **Blocking Decision**：重大合同、不可自动裁决的日程冲突、明确要 Producer 决定的人物事件；继续推进时跳转到对应详情，不弹层层模态框。
2. **Actionable / Deadline**：拼盘邀请、成员面谈、制作提案、预定舞台；可回复、委托或暂存，有时间界限。
3. **Report**：每场 Live、Weekly Review、经营与训练报告；正常不阻塞。
4. **Ambient**：成员近况、SNS、低优先级工作；可聚合与归档。

消息详情采用完整页面，而非弹窗。仅不可逆操作的简短确认可考虑 modal。Inbox 不等于唯一数据仓库；事件历史和原始报告在模块内永久可找。

### 1.3 时间推进与异常

- 默认按钮：`翌日へ` / Advance 1 Day，Inbox 和 Calendar 易于访问。
- 辅助操作：Advance 7 Days / Until Next Important Event，内部**逐日**运行所有模拟与消耗，不批量跳过结果。
- 普通商演、定期公演、已授权 Staff 的普通拼盘：结算、归档，不中断连续推进。
- **仅需玩家决定的 Blocking、用户标记为重点关注的事件、显著异常**才打断。
- 每天均能查看未来安排；对未来演出可通过专题安排会改变 Setlist、人员、关键 Part、特典政策等。

### 1.4 精细操作的入口

Reports 可以给出 **Context Action**（例如“对下一次特典会调整 slot”、“安排一场歌曲 Part 会议”），但不应直接在只读报告里改写世界状态。路径：`Report → Action Proposal → Meeting / Module → Staff Execute`。

## 2. Live 全流程、报告与周评

### 2.1 演出通用分类

| 类型 | 常见时长/曲目 | 核心经济 | Cheki / 物贩 | 主导用途 |
| --- | --- | --- | --- | --- |
| **商演 / 営業ライブ**：文化节、商场、企业团体活动等 | **1–2 首** | **固定出场费**，扣必要成本 | **无特典、无物贩** | 早期现金流托底、公众接触、上台经验 |
| 普通偶像拼盘 | 按出演时段，常为短 Setlist | 合同、ticket-back 等 | 根据活动条件 | 偶像圈新規与转化 |
| JUKEBOX AKIBA 定期公演 | 随曲库增长 | 票务／特典 | 有 | 每周实战、成员培养、粉丝关系 |
| One-man | 充分的曲库/独立集客 | 票房／特典 | 按合同与运营 | 阶段性能力检验 |
| Festival / 大型拼盘 | 按时段与舞台 | 依活动条款 | 依活动条款 | 跨团曝光和重要舞台 |

2013 年的小型拼盘供应**稀少**，故商演是关键收入来源；2014–2016 年拼盘仍不算多。2016 年末第二章起 MARQUEE祭／MARQUEE FES 等定期拼盘与后来 circuit 逐步丰富；市场供给按日期、场次系列、Organizer 关系和 Team 状态生成，不能把 2020s 的拼盘密度倒灌给 2013。

### 2.2 Performance 与前端可见性

- 所有场次照常执行**已有**逐曲、逐成员、整场 Performance／Impression／满意度模型。
- **不得在单场报告直接打印隐藏 Performance 数字**（也不显示所谓总分 78、Impression 6800 等）。
- 单场报告优先显示客观经营数据；表现的解释通过**当周 Weekly Review** 的主持人总结。
- 2014 年 7 月 **1st One-man** 第一次启用外部评论；2014 年 8 月 TIF 引入跨团观众和媒体视角；此后重要拼盘、大型 Live 可持续生成外部评论。评论在该场报告可见，Weekly Review 再提炼，不反向修改 Performance。
- 早期普通 Live 的内部意见出现在莉奈/Leader 的周报；不需要强制每场弹出点评。

### 2.3 Live Report 固定页头与数据

强制包含：

- `live_id`、演出名称／系列与序号；
- **演出日期（日本时间 JST，含星期）与开演时刻**；有实际开演记录用 `actual_start_at`，否则 `scheduled_start_at` 并标明予定；
- 场馆名称、演出类型；
- 本团动员及可区分的一般观众规模，票务/出场费/特典/其他收入与相关成本；
- 逐成员 Cheki / 写メ / 其他商品成交量、销售额、服务队列及未消化需求（场次不允许物贩则明确 `not_available`，而不是假设零需求）；
- Setlist 与参演成员、关键 Part/Arrangement 版本引用；
- 允许时附外部评论；所有底层模拟结果私有保存，供周评/调试使用。

移动端三层展示：Inbox 一行摘要 → Live Overview → Songs / Members 细节；**每个成员的 Cheki 均能在详情中查到**，默认不强迫逐个展开。日期时间在 Inbox、Calendar 与历史报告一致。

### 2.4 Weekly Review（唯一固定周期会议）

- 每周自动产生一份 Review，由**当期具体人物**主持；可亲自参加讨论，也可直接阅读后委托按 Policy 执行。
- **不设置固定月度会议**；月度财务与成员趋势是统计报表，不是会议。制作、甄选、毕业、合同、重要演出按需召开专题 Meeting。
- 周报建议只有 2–4 条真正重要观察：本周表现与趋势、突出成员、歌曲与关键 Part、Cheki 与粉丝、训练或角色问题、可操作建议。
- 观察是主持人基于同一隐藏真实结算结果的**有偏差的专业解释**。经验、关注点、对成员熟悉程度影响叙述，但不改变真实结果。
- 早期没有外部评论时，周评仅内部视角；解锁后 Staff 引用外界评价并与内部判断比较。

### 2.5 周评主持人接班（关键剧情机制）

| 剧情时段 | 主持人 | 注释 |
| --- | --- | --- |
| **序章莉奈毕业前** | **星野莉奈** | 序章无额外具名 Staff 助手；由资深成员直接提供建议、反馈和主持 Weekly Review |
| **序章莉奈毕业后与第一章** | **玩家指定的 Leader** | 可由優花、陽菜或实际任命者担任；若职位变动则按实际在任者切换 |
| **第二章** | **大崎**（制作助手） | 更强调制作、排练与二期成员培养；参与二期甄选及成长 |
| **第三章开始、第四和第五章** | **新任 Staff 助理** | 2018 年接替大崎；初期可能对成员不够熟悉，随合作加深成长 |

这里要严格区分“序章没有额外 Staff 角色”与“世界没有自动后台执行”。自动排程和事务逻辑仍在，但不拟人化成凭空出现的 Manager。主持人切换沿用同一 UI 和周报数据结构；第一次换人用 Inbox 消息演出情绪，不增加专属页面。

## 2.6 八色 Palette 与成员能力（main 锁定口径；v0.2 新增）

### 2.6.1 八色三轴语义

歌曲固有的 Palette 来自三个**相互正交**的语义判断，不来自造型、服装、官方成员色、团体形象、MV 色调或当期演出编排：

1. **Theme：Cute ↔ Cool**：作品最终要求听众欣赏的价值。Cute 侧偏向感情／关系／自我认同或成长体验值得被接受与喜爱；Cool 侧偏向掌控、执行、突破、守护或达成行动值得被赞赏。**关系是目的还是行动的团队／资源**是困难样例的重要辨别条件。
2. **Stance：Vulnerable ↔ Confident**：表达者的核心情感立场是否依赖对方确认。强势措辞不必然 Confident，告白也不必然 Vulnerable。
3. **Interaction：Witness ↔ Co-action**：真实观众是在听／看，还是被作品或有来源的现场机制赋予参与职责。歌词中的虚构「君」、故事里两人共同动作、事后粉丝自发 MIX 不自动构成 Co-action。

| 颜色 | Theme | Stance | Interaction |
| --- | --- | --- | --- |
| yellow | Cute | Vulnerable | Witness |
| pink | Cute | Vulnerable | Co-action |
| aqua | Cute | Confident | Witness |
| orange | Cute | Confident | Co-action |
| blue | Cool | Vulnerable | Witness |
| purple | Cool | Vulnerable | Co-action |
| green | Cool | Confident | Witness |
| red | Cool | Confident | Co-action |

- 严格对色：**yellow↔red、pink↔green、orange↔blue、aqua↔purple**。
- UI 色环顺序：`red → pink → orange → aqua → yellow → green → blue → purple → red`。**语义以三轴立方体为准，色环相邻仅用于 UI/几何呈现**。
- White 和 Black 不属于八色游戏 Palette；但人物的**官方成员色**仍可为白或黑，其视觉归属不应转换为任意八色语义能力。

### 2.6.2 四个不同的数据对象

| 对象 | 数据定义 | 产生层 | 对游戏 UI 的意义 |
| --- | --- | --- | --- |
| **Song Palette Direction** | 8 个非负分量且和为 1，主要色占优；有真实语义歧义才形成邻色次方向 | L2B | 单曲固有方向，制作完成后固定；不是每次 Live 的可调旋钮 |
| **Group Catalog Palette** | `Σ(song.palette_direction × song.rank_weight) / Σ(song.rank_weight)`，完整曲库 | L2B | 研究用团体作品方向；不是当前 Team Palette 或市场规模 |
| **Scenario Team Palette** | 用特定开档时间已成立、可用数据初始化；之后在游戏中按现有规则发展 | L3 → Runtime | 当前剧本时期团队方向，可与历史完整曲库明显不同 |
| **Member Palette Proficiency[8]** | 各颜色独立熟练度，**不归一化** | Member/L3 → Runtime | 描述成员适应各语义方向的能力，与官方成员色分离 |

L2B 的歌曲权重来源是本地排名派生的 `popularity_local` / `rank_weight`，**不是跨团销量或粉丝规模**。Group Catalog 聚合不按当前 Setlist、成员或剧本时间过滤；这些限制应在 **L3 Scenario Team Palette** 初始化时处理。

每首歌应从已有冻结的语义层（如 `central_thesis_ja`、带 role/strength/confidence/evidence 的 `theme_tags`、分段证据和有出处的现场互动）推导；**不得根据歌曲名、团体／成员／造型风格、排名热度或尚未审核的目标标签倒推 Palette**。L2B 的 `primary_color`、`secondary_color`、证据和不确定性用于研究/审核；游戏前端不必把所有研究置信度暴露为玩家数值。

### 2.6.3 制作、编排及 Live 的接口

- Making 产出歌曲 `title`、`theme`、`difficulty`、`appeal` 和**固定的八色 Palette Direction**；歌曲语义方向与演出时 Arrangement 分开存储。
- 玩家／Leader／助理可在训练或制作专题会议中调整阵型、演唱 Part、Lead 和排练计划；这**不会重写歌曲固有 Palette**。
- 关键 Part 的**同色／对色**关系可被已有 Performance 引擎利用，但**这里不自行发明加成数值、归一化或新公式**；需要核对游戏仓库当前实现。
- Live Report 保持具体日期、开演时间、场馆、曲目／成员、客观收益与 Cheki；内部 Impression / Performance / 满意度由周评主持人转换为可理解的观察。不把 L2 的 Palette Classification Confidence 当作演出反馈。

### 2.6.4 成员属性 V2（main 锁定）

每名成员保存 **17 项 0–20 整数属性**：

- `physical`：`agility`、`natural_fitness`、`stamina`
- `appearance`：`cute`、`pretty`
- `performance`：`pitch`、`tone`、`breath`、`rhythm`、`power`、`stage_presence`
- `mental`（沟通／创作）：`wit`、`humor`、`talking`、`teamwork`、`fashion`、`creativity`

**五维 Radar** 为 `singing`、`dancing`、`visual`、`fan_engage`、`media_appeal`。L2 Lab 的 `ability`（0–100）是五维汇总指标：

`round(5 × (0.30×singing + 0.30×dancing + 0.20×visual + 0.12×fan_engage + 0.08×media_appeal))`。

这属于**成员摘要／校准派生指标，不是 Live Performance kernel**。`overall_rating` 为 17 属性简单均值，同样是诊断字段。旧人格类隐藏属性（例如 `professionalism`、`ambition`、`loyalty`、`work_rate`）不得重新塞回 `idol.attributes`；独立的 Trait、Fan-work Adaptation、疲劳和剧情状态各用其应属模型。

UI 上人物卡可以显示已获知的 17 属性与五维 Radar（受 Producer Knowledge／观察误差约束），成员八色 Palette 熟练度应显示为另一组可理解的信息，不把它与**应援色**合并；是否显示 `ability` 汇总值按产品最终玩家可见合同决定。

## 3. Producer 与成员互动

- **不设置人物互动偏好模式**。玩家每次直接选 `Attend`（亲自交流）/ `Delegate`（由有权限的成员或 Staff 沟通并报告）/ `Follow Policy` 或 `Later`（若事情可延后）。
- 若玩家不主动找成员，成员仍与 Leader、同期、Staff 正常发展关系；日常情况通过周报转述，重要风险主动提交 Inbox。
- 主动打开人物卡可见当前有根据的交流话题。重复闲聊不会无成本无限加 Familiarity / Admire。
- “委托”导致实际工作关系成长，例如频繁委托大崎培养二期，未来成员更依赖大崎；委托不算差选项。
- 人物拥有 `Character Profile`（性格、价值观、语气、职业志向、边界）、`Dynamic State`（关系、Morale、Confidence、Role Satisfaction 等）与 `Scenario Arc`（个性化事件、对白、固定结果、条件变体）。
- 具体性格不等同能力：Trait 仍为实际专业经验，不能把“辣妹”“善谈”直接当 Trait。

首批人物库：40 多名历代 AKSB 成员化身＋约 20–25 名同期偶像化身，合计约 65–70 名，有独立化名和稳定 ID；背后用 L1 `idol_uid` 关联原型，但玩家 UI 不显示原型身份。符合年代与资格时，历史候选人在同等条件下优先进入候选池，不保送所有普通职位。莉奈、優花、陽菜已确定的三人 Portrait **直接复用，不再新设计**。

## 4. 剧情约束与自由度

### 4.1 四类来源

| 来源 | 定义 | 用户控制 |
| --- | --- | --- |
| 世界固定事件 | 市场结构、疫情、TikTok、League 等 | 应对，不能取消 |
| 人物自主结果 | 重要人生阶段的毕业/离职 | 可参与过程与时间安排，但不能无限阻止 |
| 公司上层决定 | 少量关键补员、场馆合作及资源配置 | 玩家可提出意见并负责培养，不一定拥有否决权 |
| 经营机会与条件事件 | One-man、Major、联盟合作、版权危机、集体毕业 | 根据存档可接受/错过/改变影响 |

把必须发生的故事桥梁放在**人物意志和合理的上层决议**里，而不是甄选结果之后秘密改动人数。对上层决策应明确原因、成本和历史记录。

### 4.2 极少 Bad End；困难存档跨章救援

正常通关不要求固定 Tier、动员、人数、Major 成功与否。Bad End 只在团体及公司确实不存在合理持续经营途径且重组失败时出现。章末可产生公司补员、缩编、资金重整、品牌合作等**公开、有代价的补救事件**；不能秘密添加コアファン、改写成员能力或凭空恢复版权。

连续存档全部继承；通关后开放章节选择与历史基准开局，亦可加载旧章节快照。章节评级只总结，不给隐藏免费奖励。

## 5. 序章：2013.01–2014.08（v0.6 生效总览）

> **本节替换 v0.5 之前的旧版 §5。** `2013-03 debut`、`面试可跳过`、`六首翻唱强制购买`、`2013 年 One-man/TIF` 均已废止；详细的当前实现合同见 §13–§23。

本作以 2013 年地下偶像历史为灵感，游戏人物与专属歌曲一律使用虚构身份。`JUKEBOX AKIBA` 为架空专属 Live House，2013 年五月单场出道、十二月才开始定期公演。三位创始成员为 **星野莉奈、宮原優花、小日向陽菜**；Game Start = **2013-01-07（周一，JST）**。游戏按东京当地日历推进。

| 时间 | 主线机会与活动 | 是否强制／经营影响 |
|---|---|---|
| 2013-01-07 | 创始三人开局会议、15 名书类合格甄选候选公布 | 必须完成统一面试（6 提问 AP，可不花完）及录取会议；人数自由 |
| 2013-01 中下旬 | 一套演出服、初始翻唱曲库、两首原创启动制作；团队策略会议 | 莉奈建议 6 首翻唱，不强制；训练档位与自动排期策略由 Producer 决定 |
| 2013-03 下旬 | 开始接收商演／部分拼盘邀约 | 先用已排练翻唱；不公开原创；邀请依商演供给与合同产生 |
| **2013-05** | **JUKEBOX AKIBA 正式出道** | 两首原创首次公开；8 曲仅推荐演出方案，曲少也能公演、质量由模拟决定 |
| 2013-06–09 | 持续 Live / Cheki／小型电视外务与官方 YouTube | Live 吸引、Fan Engage 留存；Staff 按策略执行 |
| 2013-10 | 人数小于 9 的公司补员决议 | 进入完全不同的第二批东京候选池，补至少九人；≥9 不强制 |
| **2013-12** | **JUKEBOX AKIBA 定期公演合作／开幕** | 机会保送；初期上座率可以低，后期经营好可满场 |
| 2014 春 | 星野莉奈毕业与 Leader 交接 | 固定剧情离队，待遇、关系、歌位交接依实际记录变化 |
| **2014-07** | **第一次 One-man** | 机会保送、演出动员和质量不保底 |
| **2014-08** | **第一次 TIF，序章结算** | 机会保送；Fans / Performance / Business 三维及综合仅展示 S/A/B/C/D/E；成员成长与关系单独进入回顾报告；继续第一章 |

三人初始 Portrait 复用，所有序章候选居住东京；真实原型的生日只用于三名创始成员，其余均为游戏虚构。初始成员正式合同 24 个月，首批常规续约发生在 2015 年的第一章，不要求序章处理。禁止假定角色自然毕业或自动按照现实原型加入／离队（有已确定脚本的莉奈例外）。

**历史机会 vs 成绩**：剧情提供出道、定期公演、2014 One-man 与 TIF 的可用合同或邀请；背景说明根据经验账本生成不同契机。活动真正举办仍支付约定成本、符合安全排期；票房、现场 Impression、成员成长和粉丝转化照常计算。序章不因低评级触发 Bad End；没有秘密免费粉丝、能力或现金补偿。

## 6. 第一章—第五章（跨章剧情约束）

| 阶段 | 日期 | 固定骨架 | 核心自由度／关联后果 |
| --- | --- | --- | --- |
| **第一章** | 2014.08–**2016.10** | 作品积累、2015 CD 权利争议、2016 年 8 月 5th One-man 机会、**10 月至少一名长期成员毕业**并以告别气氛结章 | 2016 春大谷原型的毕业是条件事件；10 月无论现役多少至少毕业一位，但不强制毕业后六人；权利争议受早期合同影响 |
| **第二章** | 2016 末–2018 夏 | 大崎参与二期甄选与培养；2018 离职；2018 Major 合作机会 | 成员/训练关系、选拔、歌曲方向、Major 结果。大崎有自己的职业理想，并非反派 |
| **第三章** | 2018 秋–2020 中 | 大崎离开后的新 Staff；二期危机；**優花、陽菜两名创始成员最终毕业**；疫情 | 二期集体决策受第二章培养、同期关系和大崎依赖程度影响；创始成员留到疫情可能失去有观众毕业 Live，不再提供二次延期 |
| **第四章** | 疫情时期–2023 秋 | 可选疫情甄选、Live 恢复、Major 资源变化、2022 现体制重组、最后一期生原型在 2023 毕业 | 历史基准下田口原型可能独自坚守，但良好存档可以保留更多成员；以重建与十年传承为主题 |
| **第五章** | 2023 年末–2026 秋 | 三名年轻残阵的历史基准、加入化名 Union 的机会、TikTok 时代、League 与高频拼盘 | 不强制把连续存档砍成三人；联盟 Fan Spillover 受风格与消费结构限制；外部商演／拼盘与体系内活动并存 |

### 6.0.1 各期甄选发表时间与跨章推进（2026-10 校准）

**时间含义**：下表为甄选的**结果发表月份**，不是招募启动、报名截止、面试、最终签约、入团或首次登台的日期。甄选实际工作须在发表前启动；具体启动日期尚未核实或冻结，不可由发表月份反推成已确认的历史事实。每期保存独立的 proposal / recruitment_start / screening / assessment / announcement / joining / live_debut 节点与各自的状态，允许有时间差。

| 阶段 | 期生 | 甄选结果发表窗口 | 对应剧情与关系机制 |
|---|---|---|---|
| 序章 | 一期／创团甄选 | 2013-01 | 三位创始成员起步，首批甄选由玩家参与；2013-10 人数不足九人时另有公司补员，与后述二期不同 |
| 第二章开端 | **二期** | **2016 年末** | 大崎主导/参与甄选培养，建立同期、前后辈、成员与 Staff 的长期关系；开始日期早于发表 |
| 第二章后期 | **三期** | **2018-05** | 在 Major 合作机会之前发表；甄选开始更早，贯穿大崎任期尾声及 Staff 交接的筹备 |
| 第三章 | **四期** | **2019-05** | 二期关系危机、创始成员交接时期的新成员融入；此前先行开展招募甄选 |
| 第四章 | **五期** | **2020-07** | 疫情条件下的甄选与培训；公告前已有选拔流程，发表不等于可立即完整现场活动 |
| 第四章 | **六期** | **2022-11** | Live 恢复与新体制建设期间的甄选；事前招募，发表后再按实际安排加入/登台 |
| 第五章 | 不再预设固定期次 | **2023-12 之后自由甄选** | 由玩家决策与队伍需求触发，不预设固定发表节点、人数或结果；仍遵守常规甄选流程 |

各期历史启发的角色/剧情保障沿用 §6.2 等既有约束，不得以甄选月份为借口暗改玩家录取、实际在籍人数或历史存档。发表月份是剧情锚点，具体候选、录取人数、合约、训练和首演产生可记录的经营后果。第二章的培养经历是第三章 Staff 离职后关系与成员请求的重要因果输入；不得直接施加全队统一情绪惩罚。

### 6.1 第一章结尾

2016 年 8 月 5th One-man 是事业高潮；**10 月的至少一位长期成员毕业**是情绪终点。用同一套 Live 结算呈现最终公演，然后以休息室告别、第二天更新名单以及新的周评主持人等 Inbox 内容渲染离别。不得为了达到六人强行删除其他成员。

### 6.2 大崎与二期

大崎是有专业理想、善于甄选和培养新人的助手；2016–2018 成员可能因长期依赖他而在离职后不安，但不设置“离职→全体自动降低 Morale→集体毕业”的硬链。

- 月城美心（**つきしろ みこ**，津代原型）：大阪出身、2016 年末高中生、有舞蹈训练背景；被选中后**固定成功上京**。私人事件《東京へ行きたい》负责展示家庭交涉，而非取消录取。由大崎出面且交涉前现役人数 ≤9 时过程顺利；玩家亲自去则依据第一章信誉、未兑现承诺、公司生活保障等决定能否一次谈妥。无论初次是否顺利，剧情支持继续协调并最终上京。
- 小此木原型化身与美心同期进入团队，由上层针对核心人物的专项支持招募保证剧情人物出现，但普通甄选仍自由。共同上京、排练、远征创造强关系成长机会；亲密关系会促进职业意见交流，**不是必定集体毕业**。
- 若二期非常依赖大崎，第三章开局更容易出现不安和联合请求；若 Producer、Leader 与其他 Staff 长期提供稳定支持，可显著缓和。

### 6.3 2019–2020 创始成员的“错过最佳告别”

两名创始成员早已产生毕业意愿。玩家影响力、对后辈的责任与交接压力可以让她们继续留队，**她们的专业表现依然稳定且对团队有正面贡献**，不得通过不合理 Attr 衰减作“惩罚”。如果长期挽留至疫情，原定毕业 Live 可能无法举行，且**不再提供再次延期毕业选项**。这是一种悲剧性的遗憾表达：放手太晚可能错过最美好的句号，而非数学上的 Bad End。

### 6.4 第四、五章市场差异

第四章从疫情停演、配信、现金流压力到逐渐恢复；2022 历史基准可能出现仅一位老成员坚守。第五章加入虚构大型 Union；例如联盟内高频拼盘、Fan Spillover 与赛季制 League，并保留一般真实拼盘/场馆名称。短视频曝光先影响新規，不直接无条件加コアファン。

## 7. 可追溯的数据契约（建议 schema，不与现有引擎重复造轮子）

| 对象 | 需要的字段／关联 | 边界 |
| --- | --- | --- |
| `ScenarioEvent` | `id, chapter, window, trigger, participants, choices, fixed_outcome, consequence, fallback, deadline, blocking` | 剧情解释与发起，不直接替换引擎算式 |
| `CharacterProfile` | `fictional_id, source_id_internal, alias, portrait_ref, voice, values, career_goals, boundaries, dialogue_hooks` | 历史原型内联仅开发可见，防止玩家 UI 显示真实身份 |
| `CharacterState` | 引擎已有 Attr/Trait/Palette/Morale/Relations/Role 等引用 | 不复制第二份可漂移的数值 |
| `Meeting/Delegation` | `request, owner, attend_or_delegate, delegated_to, due_at, summary, relation_effects` | 后台执行产生真实关系与信息差异 |
| `LiveEvent` | `live_id, series, type, venue, scheduled_start_at, actual_start_at, setlist, lineup, contract` | JST、准确开演、同日多场可区分 |
| `LiveReport` | `live_id, audience, attendance, ticket/fee, merch, cheki_by_member, queue, costs, reviews` | Performance 真实数值仅引擎内，前端不直显 |
| `WeeklyReview` | `week_start/end, host_character_id, cited_live_ids, factual_highlights, interpretation, recommendations` | 使用当期实际主持人；不添加固定月会 |
| `Song` | `title, fixed_palette, theme, difficulty, appeal, creator_contracts` | 五项生成值；固定 Palette；具体数据形状遵从新 Spec |
| `Arrangement` | `song_id, version, assignment, formation, familiarity` | 关键 Part 颜色匹配遵从新 Spec |
| `ChapterSnapshot` | 世界状态引用、章节事件结果、主持人变更、人物履历、财务、曲库、粉丝 | 连续继承；历史基准另存；不偷偷改库存 |

**所有定期演出、商演与拼盘都使用相同 Live Engine**。区别是类型配置与合同条件，不是三个互不兼容的简化结算器。

## 8. 实现顺序与验收

### P0：可运行序章垂直切片

1. 四导航 mobile-first、Inbox 完整页详情、日推进与事件中断。
2. 三名创始成员、已批准 Portrait、莉奈主持 Weekly Review；虚构剧本初始状态。
3. 商演合同（1–2 曲、固定出场费、Cheki 禁用）、普通少量拼盘、统一报告。
4. Making 最小五字段生成与创作者委托，复用最新八色 / Performance / Formation 引擎。
5. 2013 年 10 月人数不足九人上层补员，12 月 JUKEBOX AKIBA 定期公演。
6. 成员级 Cheki 明细、Inbox 报告、周评叙述；Live Report 不展示 Performance 分数。
7. 莉奈毕业与 Leader 主持切换；普通 Live UI 运行 1st One-man、TIF，并解锁外部评论。
8. 2014.08 ChapterSnapshot 与续玩入口。

### P1：跨章人物与经济

2015 版权合同事件；2016 10 月动态毕业；大崎招募和二期关系；2018 组织转移；2020 疫情状态；2022 重组及 2023 联盟剧情。

### P2：内容丰富度

全体 65–70 人角色卡、个人对白与多个历史基准章节快照；丰富 Creator 歌曲种子库；外部评论变体、League 赛季规则。

### 验收案例

- 序章三人直接出道，10 月公司补员到九人，12 月开始有报告、有收入和成长的定期公演。
- 另一存档 1 月甄选约 15 人，允许选拔，10 月不自动补员，非选拔成员仍可培养和沟通。
- 商演无 Cheki 且仅出场费；普通 Live 的每位成员 Cheki 均可从报告查到。
- Live 报告日期、星期、JST 开演时间准确；同日双演出不混淆。
- 逐场隐藏分数不暴露，周评根据同样底层结果能提出可核实的具体建议。
- 毕业后 Weekly Review 主持人真实更换，历史报告不会被新主持人重写。
- 1st One-man、TIF 无特制 UI 依然能产生外部评论与章节情感效果。
- 任意正常艰难存档可跨章继续，补救有明确代价和历史记录。
- 玩家完全不主动个人聊天仍可收到 Staff/Leader 报告；深度互动只增加信息与人生叙事，不提供刷数值捷径。

## 10. 序章事件触发器与前后衔接合同（v0.3 新增，设计提案）

> 适用范围：2013-01 至 2014-08。这里把 §5 的剧情时间线转为可实现的 **事件状态机**。日期窗口中尚未由史实或产品敲定的具体日号全部是**参数/建议**，不是虚构的历史事实。每个事件的“演出机会必达”不等于“玩家必须成功”。

### 10.1 事件引擎规则

**两套并行状态**：`world_time`（逐日推进）与 `story_flags`（触发/决议/后果）；人物、财务、Live、招募人数和歌曲库存始终读真正运行时实体，不能维护另一套剧情假计数。

事件阶段：`DORMANT → ELIGIBLE → OFFERED → RESOLVED / EXPIRED / SUPERSEDED`；对于长期弧线允许同一 `arc_id` 有多个不同 `event_id`，每个独立幂等。对话结果与实际执行结果分开，例如合约 `ACCEPTED` 后还要等真实 `live_id` `COMPLETED` 才算事件终结。

**触发顺序**（每个游戏日只做一次确定性状态事务）：①执行前一日已排定的世界/人物变化 → ②评估已到期的选择与安全兜底 → ③评估已达条件的新事件 → ④根据 priority 与互斥组入 Inbox → ⑤执行玩家决议 / Delegation → ⑥模拟当日并结算 Live → ⑦产生报告与下一日候选事件。已解决事件不得二次入队，后续延迟事件要检查依赖 flag。

- **时间窗**：`earliest_date`、`target_date`（可选）、`latest_date`；`latest_date` 是必须落地的事件使用的兜底边界，不要求每个随机事件都触发。
- **资格**：`prerequisites`（其他事件结果）、`predicate`（现有角色/经营状态），`exclusions`（冲突事件/不可用成员）。条件只决定**变体**时不应阻断必达节点。
- **互动**：`blocking=true` 只表示必须选择；Review、Live Report 与常规商演不阻塞。限定次数的提醒可自动 Delegate；关键人事决定不可默默代办。
- **抢占**：同日多项 blocking 时按 `character_departure > chapter_gate > board_decision > contract_deadline > optional_interaction` 排序；处理一件再重新评估，避免在弹窗中假装同时更改 roster。
- **兜底**：机会由公司/场馆/人物意志真实提供；预算不够、没有歌曲、参演人不足时改变规模、申请合理资助或生成违规/违约结果，**不能凭空清除费用、歌曲缺口或强行提高能力**。
- **可追溯**：每个事件记录 `triggered_at`、`resolved_at`、`conditions_snapshot`、`decision_actor`、`choice`、`outcome`、`linked_live_id`、`effects`、`fallback_reason` 和后续引用；读档后重播不重复发奖/补人。

### 10.3 关键前后分支规则

**A. 首次甄选 → October Gate（不重复强制招募）**

- 1 月不甄选：三人可以完成首演和春夏商演；10 月人数 `<9`，上层按差额支持补员。
- 1 月招募 15 名：最多 18 人；允许固定选拔、轮换、全员出演，10 月 `≥9` 不补员；“甄选 15 人”是可实现变体，**不是默认强制人数**。
- 9 月已主动补至九人：10 月不触发上层甄选。10 月核对时有人已正式离队，应按实时 active 人数判断。
- 补员事件已经决议后，新成员因其他真实剧情离开：不再反复激活 `P07`；由普通招募/经营压力处理，避免10月死循环。

**B. Early Venue vs December Residency（不可相互抵销）**

- 12 月是公司层面确定的**定期公演开始**，不是玩家通过前期 Live 次数解锁的奖励。
- 提前在同一场馆上台是可选的散场演出；绝不把可选早期演出标记为 `first_residency_live_completed`。
- 特典会只有允许的合同类型开放；早期商演从定义上不得开展 Cheki/物贩。

**C. 莉奈意向 → 毕业 → Leader → Weekly Review**

- 离队意向至少设置两段不同事件的伏笔，但不因为玩家忽略交流而隐藏毕业；她本人会提出。
- 对话选择影响她与团队的交接、毕业演出质量以及以后是否愿意偶尔帮助创作，**不改变固定毕业**。
- 周评主持人由 `weekly_review.host_character_id` 在**生成时**快照：毕业前生成的历史周评依然是莉奈；毕业后由已任命 Leader 主持。跨毕业的那一周按周评实际生成/主持日期决定，必要时 Leader 引用莉奈此前的记录。
- 原关键 Part 失去成员后 `arrangement_needs_review`，可 Staff 默认修补，不阻止其他演出无限期发生；特殊失配在后续周评体现。

**D. One-man → TIF → 第一章**

- 7月 One-man 解锁外部评论**功能和档案内容**，不是解锁 TIF 邀请的隐藏门槛。TIF 可以提前邀请，甚至邀请通知在 One-man 之前。
- 外部评论由已有 Live 的观众、歌曲及成员结果推导；不能让“外评好坏”直接修改引擎已算出的表现。
- TIF 的 Live 实际完成与“收到邀请/已排演”三者是不同 flag；章结必须记录最终是否出席，不可用 `tif_invited` 冒充 `tif_completed`。
- 章末导出初始下一章：`roster + leader + skill/palette_proficiency + song_catalog/arrangements + team_palette + fans + finance + relations + event_history + live_history`。World Palette 随世界时间继续变化，并非从新章重抽。

### 10.4 周评与事件收敛机制

- 每周周评仅一份，人物主持人根据实际剧情身份生成；序章**没有新增具名 Staff**。莉奈毕业后由 Leader 代主持。普通周报不是 Blocking。
- 日常事件池的频率采用 cooldown、budget、类别权重控制：同一成员/同一主题未结束之前不出现重复请求；紧接着结算的大量 Live 可以在当周周评中合并分析。
- `Priority` 中 **人物承诺/公司决议** 高于随机日常；已安排重要演出自动占用相关时间，不允许同一时刻虚构出多个亲自出席。
- Live Report 仍即时发送且准确显示日期、开演时间、Cheki/票务等客观项；Performance 精确数值隐藏，隔周或当周的 Weekly Review 做自然语言总结。
- 连续推进逐日检查触发，并在 Blocking 或玩家关注的演出出现时中断；对普通低价值通知可自动归档。**不设计固定月会**。

## 11. 剧情证据 × 人物性格 × 经营反馈（v0.4；序章正式设计）

### 11.1 目标和硬边界

**最终体验**：玩家通过制作歌曲、安排阵容、培养偶像和参加演出积累可回溯的经历；故事角色从这些真实经历出发，以符合自身性格和利益的方式解释变化、发起行动。大型机会由剧情保证其**发生窗口/提供方**，但不向玩家透露日历保底或触发器；角色永远不能宣称某件根本没有发生的成功。

此设计覆写 §10 中可能产生误读的部分：
- `P09_RESIDENCY_CONTRACT` **只由叙事链引入与公司/场馆合约落地**；与单纯的普通 Live 积分、粉丝数、日期达标无直接自然解锁关系。公司先取得合作，之后定期排期才能自动运行。提前在 JUKEBOX AKIBA 的偶发演出不自动生成定期驻场。
- 序章 **大型 One-man、TIF 只能由预先配置的剧情链产生机会**，不能由日常邀约池、世界活动生成器、达标算法额外生成。玩家成绩影响主办方条件、报价、宣传、关系、评价和后果；不否定机会本身。
- 普通商演、小型拼盘可以由世界中的真实承办方/活动库、公司业务渠道产生邀约，满足已有约定才进入 Staff 自动排期。**自动排期不能凭空生成 Live 机会**。
- 关键故事的“奖励感”来自前期积累 → 他人注意 → 正式机会，不展示 hidden gate、剧情章节数值或“系统奖励”字样。
- 剧情事件不能直接修改 Live 内核结果。外部评论最早在 2014-07 首次 One-man 显示；此前“有人注意到团队”只能是有来源的私下意见、后续合作询问、艺人与工作人员对话，不能伪装成公开外部 Live 评论模块。

### 11.2 统一架构：一个事实账本，三层推导

1. **Experience Ledger（事实）**：由现有系统写入，例如 `live_completed`、`song_released`、`arrangement_changed`、`first_paid_gig`、`member_training`、`member_assisted`、`fan_growth`、`cheki_queue_overflow`、`member_tension`、`cash_crisis`。每条附 `source_id`、发生日期、在场人员和客观事实；涉及演出表现的底层数字只供引擎和叙事判断，不能公开。
2. **Character Appraisal（人物解读）**：同一个已发生事实，角色按价值观、职业目标、注意力、对参与者的关系、信息可得性、当时情绪，生成不同的 `observation`、`feeling`、`intent`。这是**有信息边界的解释**，不是新事实或改写历史。只有亲临现场/收到转述的角色才有相应亲历知识。
3. **Story Arc（行为/事件）**：脚本读取事实锚点、人物意向和持续中的机会或压力，决定哪个对话/行动被人物提出、谁作决定、如何执行及后续有什么后果。最后将行动与结果再写入事实账本。

事实与人物观点分离：`fact` 可复查，`appraisal` 可有偏差或误解，`narrative_line` 可带情绪，但不得捏造发生过的事实。

### 11.3 最小角色模型：塑造个性但不新增伪属性

每个重要角色配置的**作者型叙事参数**（不算 17 项 Idol Attr，不把性格变成另一组强行公开的隐藏能力分）：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `values` | 重视什么，以及冲突时如何排序 | 团队稳定、被认可、个人创作自主 |
| `career_goal` | 未来希望成为怎样的人 | 创作、舞台中心、照顾后辈 |
| `voice` | 言语风格和习惯 | 活泼直说、温和谨慎、专业具体 |
| `attention` | 首先注意哪些事实 | 新人成长、现场气氛、成员压力 |
| `social_role` | 当前责任/权力 | 老成员、Leader、制作助手 |
| `knowledge_scope` | 本人已见、受托报告、推测 | `observed_live_ids`、`secondhand_reports` |
| `relationship_refs` | 对他人基于历史互动的看法 | 同行、前辈、对抗、信任 |
| `commitments` | 已作出的决定及兑现期限 | 莉奈决定转向自己的事业 |
| `narrative_arc` | 允许的剧情成长和不可逆限制 | 协助新人→考虑独立创作→毕业 |

角色的真实技能仍通过 17 Attr、Trait、Palette 熟练度与经历模拟；叙事参数只负责**关注点、解读、行动选择和语言表达**。避免将「勤奋」「忠诚」「野心」伪装成新数值以替代已移除属性。

**作者设定（虚构，不作为真实原型人物的心理事实）**：
- **星野莉奈**：经验丰富、热情，乐于向 Producer 解释现场和照顾新人；有越来越明确的独立创作志向。前期周评常先谈“谁进步了、谁需要支持”，欣慰与焦虑可以并存；她的毕业是自主职业决定，关怀能改变交接和关系，不能永久改变去意。
- **宮原優花**：外向、坦率，有时从形象、气氛、执行和队伍士气切入；担任 Leader 后渐渐学会报告与协调。对资源紧张更可能直接提出具体解决办法。
- **小日向陽菜**：温和、善于观察少数成员的微妙情绪，倾向先关心成员是否能跟上；担任 Leader 时可从谨慎报告逐渐成长为有独立判断的人。
- **公司上层**：优先考虑可持续经营、合作合约、训练与团队规模，不是恶意反派。上层要求十月扩至九人，是已预设的组织决策，解释依存档状态变化，但不会冒充成员自发意愿。
- **大崎**：仅第二章引入；重制作、培养和方法，对二期成员形成信任；不能倒灌到序章。
- **新任助理**：第三章以后引入；初期专业但对团队认识浅，经过共事累积信息；不能倒灌到序章。

### 11.4 事件“因果证据选择器”

每个重大事件维护至少三类**有事实依据**的叙事版本：

| 事实类别 | 能讲的理由 | 不能讲的理由 |
| --- | --- | --- |
| Live/观众反馈出色 | 演出组织者现场看到了稳定的表演、团队执行有进步 | 虚构某位经理“高度评价全场”却没有在场或有效转述 |
| 歌曲和训练成果突出 | 新歌完成、成员磨合、节目更完整，引起公司合作兴趣 | 未完成曲目就说“这首新曲大获成功” |
| 成绩一般但坚持运作 | 持续商演、团队出勤、公司为培养项目争取试验性场地 | 宣称票售罄、粉丝激增等不存在的成绩 |
| 财务危机 | 公司谈成低保底/分成合约，但需承担真实成本或义务 | 免费抹除亏损、用赞助瞬间填平现金缺口 |

选证据次序：**可验证 + 可关联提供方 + 近期/重要 + 与当前角色一致**。为避免重复，可以优先引用尚未在最近两次关键剧情里使用的事实。确无充分绩效证据，诚实引用“连续工作”“公司培养计划”“主办方愿意试办”；不能捏造成名故事。

`evidence_refs[]` 必须至少含一个实际 ledger 引用，或标记 `world_contract_source`（真实配置的机构/公司行为）。不强求每个节点都有“表现出色”的证据。

### 11.5 性格影响选择，但不可任意夺走玩家自由度

人物发起请求遵循：
`观察到的事实 → 私人评价 → 情绪/职业目标 → 可执行的请求 → 玩家决定/委托 → 实际后果 → 更新关系和下次解读`。

三种独立影响：
- **说什么**：同样的 Cheki 队列，莉奈可能先心疼新人，優花更直接提时间分配，陽菜注意成员是否疲惫。
- **为什么主动来**：某人重复承担难的关键 Part 且在队内缺支持，更容易提出训练或位置调整；未察觉则可能通过 Leader 周报转述。
- **以后怎样变化**：玩家帮助、拒绝或委托不强迫固定人格翻转；改变合作记忆、相互期待、可获得的信息和下一次事件选项。

不能做的事：
- 用性格模板凭空宣布能力涨幅、粉丝暴涨或演出成绩；
- 以“喜欢 Cool 的角色不能做 Cute”为禁令；
- 允许高关系值取消莉奈确定的毕业；
- 为制造 drama 让人物知晓 Producer 隐藏界面之外的内部真实绩效数字。

### 11.7 序章具体 Inbox 剧情事件（内容草案）

以下文本是**虚构对话稿草案**；引号中的“某人看到演出”等内容只有匹配对应 ledger 证据时才能选用。

**E01 · 第一份 Weekly Review（2013-01，莉奈）**  
前置：开局已接受介绍，有一次训练、试听或制作更新；未曾发送此事件。  
Inbox（非阻塞）：「今天把大家排练的情况整理了一下。陽菜在仔细记动作，優花倒是很快就能把气氛带起来。关于第一场演出，我们先从真正能做好的一两首歌开始吧。」  
可选讨论：让她提出曲目建议／讨论甄选新人／照既定计划继续。  
后果：记录被咨询事项与莉奈-Producer 合作记忆；绝不直接授予 Performance buff。

**E02 · 第一次付费商演后的回顾（2013 春夏）**  
前置：`first_paid_gig_completed`；合同属于商业短演；成员名单真实。  
Inbox（非阻塞）：「出场费到账了。今天虽然只唱了两首，但让大家在不熟悉的观众前完成演出，本身就是经验。」  
变体：如表现失稳，莉奈会提“某段仍紧张”；如排练进步则提“比上周稳了”；两者不使用数字。  
后果：经营现金流真实入账；莉奈在下一次周评引用实际场次。**不生成 Cheki/物贩**。

**E03 · 一次不明确的关注（2013 夏秋）**  
前置：有完成的商演或小型拼盘、可追溯的工作人员/公司渠道；没有证据则使用“公司已联系潜在合作方”的分支。  
Inbox（非阻塞）：「公司说，之前合作的活动方愿意再谈一次。是不是能让我们有更固定的出演安排，我也不敢保证。」  
人物反应：莉奈兴奋、但仍提醒不要让新人疲劳；優花更关心曝光与排期；陽菜关心准备是否充分。  
后果：写入 `venue_contact_started`，不直接创建驻场合约。

**E04 · 定期公演提案与交接（2013-11 至 12）**  
前置：`venue_contact_started` 或带来源的公司主动场馆开发；公司与 JUKEBOX AKIBA 达成合作条件；不以 Performance/Tier 为硬门槛。  
Inbox（阻塞，仅需对运营方案决策）：「一直跑不同的现场，终于有机会在一个地方持续演了。公司谈成了十二月开始的固定档期。莉奈，你觉得呢？」  
莉奈：「如果能每周站在那里，新人一定进步得快。不过大家上场的机会，最好现在就商量好。」  
优花/阳菜各按性格补充实施问题。  
玩家可选：主力固定出演／新人轮换／尽量全员；选项接现有 Team/Live Policy，不额外创设剧情编队系统。  
落地：`regular_contract` 存档并按规则自动排期；**绝不是普通 Live 自动排期导致合作自发产生**。公司成本/分成/最低场次是真实义务。

**E05 · 十月人员调整（2013-10）**  
前置：读取当日真实签约活跃人数。若 `<9`，由公司下达至少补到九人的计划，玩家参与甄选与合同。  
莉奈：「新成员一多，光是选谁站前面就不轻松了。不能只看谁现在最会跳，要想想半年后她们能成长成什么样。」  
优花若人多，可能担心轮换公平；阳菜可能留意被选不上舞台的新人。  
若 `≥9`：本事件为一般人员近况通知，不发生补员。  
后果：真实 roster 更新；不得二次执行、不得偷偷把玩家明确拒绝的候选加回来。

**E06 · 莉奈的选择（2014 春）**  
前置：至少一次事业方向伏笔已经送达；职业决定窗口到；莉奈在队。  
她主动提出：「在这里一起走到现在，我真的很开心。但我也想试着做只有我自己能决定的东西。」  
选项：先倾听并共同筹备告别／集中精力完成交接／表达不舍并继续谈。所有选项尊重她的决定。  
后果：告别体验、关系与以后可联系性不同；不改变毕业。毕业后写 `arrangement_needs_review`。

**E07 · 第一份新 Leader 周评（2014 春末）**  
前置：莉奈已毕业、`leader_id` 已任命、下次 `weekly_review_created`。  
若優花主持：「以前都觉得她写报告很轻松，轮到我才知道要顾的事这么多。我想先把下周练习和出场安排定好。」  
若陽菜主持：「我还没有莉奈那样会讲，但大家这周的变化我都有记下来。先从一件件做起吧。」  
后果：不同解读/下一条建议，但相同事实与结算。若 Leader 另有人选需对应 persona fallback。

**E08 · 1st One-man 机会（2014 春末至 7 月）**  
前置：公司筹备/与场馆接洽已发生；可引用多次定期公演、曲库扩充、粉丝支持；表现差则说“需要一场真正检验我们的专场”。  
Inbox（阻塞筹备）：公司通知：「这次我们不再只借别人的舞台。七月，试着办一场自己的公演吧。」  
Leader 可表达兴奋或压力，但不论哪种情况都不能假定售罄。  
选项：保守预算／追加宣传投资／优先保障全员出演。进入普通 Live 和 Finance 决策，不能额外生成大型 Live UI。  
后果：创建剧情专属 One-man 机会和真实演出合同；首次外部评论在演出结束后出现。

**E09 · TIF 邀请与序章总结（2014 夏）**  
前置：公司/主办方的联络已成立，TIF 节目机会窗口到；可与 One-man 并行筹备。  
Inbox（阻塞安排）：「夏天，有更大的舞台愿意给我们一次机会。这次会有并不认识我们的观众。」  
Leader 会根据性格与真实 Setlist 资源提出不同策略（突出最成熟曲目／展示更多成员／冲击新规）；Player 选择并进入普通 Festival Live。  
后果：是否出演、动员、成本与外部评论都按实际 Live 运行；章末由当期 Leader 回顾**真实记录**，不颁发虚构达标奖章。

### 11.8 人物立场与玩家选项相互塑造：记忆，不是脚本分数

建议记录的可回顾 `relationship_memory`：
`actor_id, target_id, context_event_id, fact_refs[], decision, interpreted_as, timestamp, persistence, resolved_state`。

示例：
- 玩家鼓励新人轮换上场 → 新人有真实的上场机会；莉奈解读为愿意培养后辈；优花可能担心主力表现但赞赏公平。
- 玩家持续只让少数成员承担难的 Part → 她们可得到更多演出经验，也可能疲劳或产生地位不平衡；其他成员依据各自目标表达不同期待。
- 玩家安排莉奈毕业前指导接班 Leader → 后续 Leader 周评能引用真实共事记忆；若没有安排，则不会凭空怀念共同完成的“交接计划”。

原则是**世界数值驱动真实经历，人物对经历作差异化解释，解释又通过自主请求和玩家选择改变未来经历**。不要为几句对话直接发放一堆隐形好感度。

### 11.10 与 World Palette、Setlist 和周评连接

- World Palette 具有 **Popularity 与 Saturation 两个独立维度**；潮流变化和竞争饱和只影响歌曲选择、现场受众表现以及公司对项目的经济判断，不改变序章剧情桥梁的基本可获得性。
- 单场 Live Saturation 由具体 Setlist 的 Presented Palette 累积；同色曲目多意味着可选曲序和避免疲劳的空间有限，但跨色组合也需要相应的歌、Member Palette Proficiency、编排熟练度和气氛连续性。
- 周评角色可以说「连续类似的歌让中段反应趋于平淡」，前提是内部模拟确有相应结果；不展示隐藏原始 Performance/Impression 数字。
- 莉奈、Leader、后续大崎和新助理对**同一市场和演出证据**关注点、表达和建议不同，但不修改真实性。序章无额外具名 Staff。
- 每场 Live Report 依旧只即时展示日期、开演时间、观众/票务/逐人 Cheki/收支等客观数据；第一次外部评论始于首场 One-man。

### 11.11 实现步骤及验收（增加到 §8）

**阶段 A — Evidence Ledger**：实现事件引用协议与角色信息可得性；保证同一场 Live 有稳定 `live_id`，并能回查成员、歌和商业结果。

**阶段 B — Character Appraisal**：先只做莉奈、優花、陽菜三人；每人三类观察模板（成长、经营、成员关系）与两类关怀/建议动作。定义同一事实不同人物的可复现表达。

**阶段 C — Main Event Arcs**：接入 E01–E09，保持现有 `P00–P19` 事件主链；E 编号为内容包而非第二套主线状态机，避免双重触发。

**阶段 D — Weekly Review & UI**：报告能引用 `fact_refs`，具有正确主持人，剧情会在 Inbox 及专题会议发生；无月会、无专属 One-man/TIF 页面。

**验收测试**：

1. 2013 春商演表现平庸：年底也出现合法驻场合作，但 NPC 不会谎称广受好评。
2. 商演极少：场馆机会应改由公司业务开发解释，而非捏造多场被看见的演出。
3. 玩家有高评价新歌：优先引用实际发行/完成的歌曲和相关事实。
4. 10月已有≥9人：公司不再增员，莉奈不讨论“即将到来的强制补员”。
5. 十月补员后新人失去上场机会：人物按各自价值观提出不同请求。
6. 长期只唱 Pink、World Saturation 上升：周报可以反映重复风格疲劳，但没有内部直接分数。
7. 莉奈离队：她不再出现在新的主持人回复中，旧周报与记忆保持原样。
8. 玩家没有安排毕业交接：Leader 不应说“莉奈亲自手把手教过我交接工作”。
9. 2014 One-man 动员不佳：外部评论反映不佳而 TIF 机会仍可来自独立主办方渠道。
10. 快进、存档重载、同日多剧情：不重复合同、评论、角色请求；每份关键文本都可追溯证据。
11. 大崎出现在 2013：必须失败；这时尚未登场。
12. 所有公开文本不得包含 `scripted_gate`, `fallback`, `threshold`, `guaranteed_event` 等内部术语。

## 12. Live / Member / Weekly Review 反馈节奏与里程碑（v0.5 追加）

## 1. 原则

借鉴 Chikadol Sim 试玩中**每场 Live 的即时可见结果、微小进步的成就感、现场流程感**，而非照搬其从零粉丝起步的经济数据或强迫逐次手动操作。Chronicle 仍由策略会议决定团队政策，Staff 自动排期，Producer 处理重要抉择。

**统一三级反馈：**
1. **Live Report**：每次活动结束即时提供实测运营数据（日期、场馆、出演、动员、票务／出演费、逐成员 Cheki 销售、经营收支）及可由表演系统推导的**定性**舞台观察。严格隐藏 Performance／Impression 原始内部数值及粉丝隐藏状态。
2. **Member Feedback**：仅在真实成员可观察、可转述的事情出现时触发可选短消息；例如某成员记得重复来排队的熟面孔、听到观众称赞、第一次拥有明显自己的队列、经历舞台失误。成员的话属于**局部观察或主观感受**，不得伪装为已核验的粉丝转化因果。无观察可无消息。
3. **Weekly Review**：当周 Leader 引用多场实际 Live、训练、外务、收入、成员反馈，概述变化趋势与可执行建议。不重复照抄每场 Live Report；仅首次遇到新机制时充分解释，重复场景缩短。生成时快照主持人，莉奈毕业后由当时 Leader 接替。

## 2. 信息来源与因果边界

- 现有粉丝模型是 Public / Otaku / Core 的**聚合概率转化模型**；初次到场受 YouTube、电视、个人外务／宣传曝光与活动条件影响；Live 表现主导初次吸引，Fan Engage／特典会体验主导留存，舞台表现次之。**后台不记录某名粉丝因何转化，也不新增按人因果系统。**
- 报告不得输出诸如「这三名粉丝因为宮原的歌加入」之类无法观察的确定归因；也不展示精确的隐藏粉丝分类转化值。只有工作人员实际掌握的购票／销售事实可以数值化。
- 可根据真实 ledger 生成定性评价，如「第一首原创反应很好」「今天七海的 Cheki 排队较上周长」；在存在对应记录时，偶像可说「有人告诉我看过 YouTube 才过来」，但该陈述不作为全体新客的统计依据。
- 未开展问卷、采访或粉丝身份追踪时，不显示未经核验的来源份额。Member Feedback 不参与再次加粉丝，防止双重结算。

## 3. 展示密度

| 场景 | 默认呈现 | 展开条件 |
|---|---|---|
| 普通拼盘／商演 | 快速 Live Report、一句定性重点、可选成员短消息 | 新机制首次发生、异常、重要人物里程碑 |
| 首场商演／五月出道／首场定期公演 | 开场→关键歌曲／MC→特典会→报告的分阶段回顾 | 第一次完整教学必达；以后可快进 |
| 2014 首次 One-man／TIF | 分阶段重要 Live 回顾；可引用历史事件 | 主线舞台必达，动员与表现不保底 |
| 平时训练／外务／视频 | 非阻塞 Inbox／Calendar 变更 | 影响合同、安全、重大机会时再阻塞 |
| 周评 | 1–3 条趋势、0–2 条建议 | 缺乏新观察时压缩，不强制月会 |

**新手教学递减**：一个概念第一次触发提供清晰解释；第二次仅提变动；日常重复时不弹同样提示。时间推进可以按日或 +7 日执行，重大可决策事件自动停下。

## 4. 小型里程碑和四次回顾

小里程碑：成员第一次有稳定 Cheki 队列、初次完成重要 Part、首次个人外务、某首歌正式掌握、团体首次定期公演取得较好动员。这些以 ledger 的真实可观察事件为依据，可以有一则人物对话；不要模拟具名粉丝 NPC，也不硬性每周安排里程碑。

- **2013-05 出道**：回看三人创始会议、首轮招募与两首原创首演。
- **2013-12 定期公演合同／首场**：回看阵容调整、曲库、稳定观众的形成；签约是机会，成效由经营决定。
- **2014-07 首次 One-man**：回看此前的练习、成员角色与真实动员，不因剧情保送而伪造成功史。
- **2014-08 TIF 后**：三项仅显示字母评级：Fans、Performance、Business；另展示综合评级（同为 S/A/B/C/D/E），历史参考综合 B，不展示内部数值，不触发 Bad End。成员成长、关系、Leader 更替与毕业保留为独立的事实性回顾，不再作为第四评分项。各项与综合评级允许不同。

回顾是 Experience Ledger 的**只读聚合／叙事表达层**，不重复发放数值奖励。此前事件缺乏证据时，改用中性叙述，不补造人物经历。

## 6. 验收用例

1. 同一场结算的 Live Report、Member Feedback、Weekly Review 引用相同 `live_id`，不会重复计算粉丝和现金。

4. 2014 年莉奈毕业后，历史周评保持旧主持，新周评由任命 Leader 主持。
5. 仅首场重要 Live 默认分阶段完整教学，普通多场 Live 允许快速推进。
6. 四次回顾自动从历史取证；差经营路线也会收到机会，不获得保底成绩。
7. 序章普通商业演出既有的场贩／Cheki 权限按活动合同执行，不能因反馈展示而虚构特典会活动。

### 13.3 最小事件运行规则

- `idempotency_key = save_id + event_gate + scenario_instance`；跨读档不可重复收奖励、重复签约或重复完成 Live。
- 保存 `scheduled_at`、`opened_at`、`resolved_at`、`actor_id`、`fact_refs`、`player_choice`、`result_ref`，并用事件账本生成叙事依据。

### 14.2 统一面试与人物三种面板

面试不可跳过，15 人同场统一试唱及短舞蹈，**仅在列表输出模糊结果**。Producer 另有 6 AP，提问一次耗 1 AP，不必花完；允许向同一候选或不同候选询问合法问题。`Card / List / Detail` 共用 `known_character_profile`，真实 17 Attr 只用于模拟，评审五轴 Radar 用估计**区间**而非具体数值，三人评审意见允许分歧和误判。

- Card：人物肖像、生日/学校、类别、宽幅推测、是否入短名单。
- List：15 人统一试唱/舞蹈定性报告、筛选、拟录取对照，禁止泄漏排序真值。
- Detail：履历自述、问题回答、三人有来源的意见、宽幅五轴雷达、有限 Trait 与以后积累的历史。
- 面试完成后再开三人会议决定初始阵容和 Leader，推荐从 15 人中录六人使总团体九人，**允许任何实际录取规模**。10 月少于九人的公司补员是独立剧情，且不替玩家秘密录取曾拒绝的人。

### 14.3 两年期合同、续约与终止

- 序章活动合同 24 个月，`Low ¥5,000/月 + Cheki 可分配净额20%`、`Medium ¥10,000 +30%`、`High ¥20,000 +40%`。为统一合同模板，三名创始成员和新成员同档。个人外务按照**专用**收支规则，不与 Cheki 提成重复。

- 第一章开始：Staff 汇总续约意向 → 玩家一次决策「续约/升级全职/期满不续」→ 本人接受/拒绝 → 批量办理；离队可正常毕业或不续约。**不得把表现不好直接当作开除**。

## 15. 生产、曲库和 Live 可用性

### 15.1 初始制作

- 创建两首原创：各 ¥180,000 制作预算（TUNABLE）；至少 4–8 周的外部音乐制作，之后编舞老师负责原创曲的编舞**和歌曲正式训练**。此处「初期不请老师」仅指**不聘任常驻教师**；编舞老师是项目制作服务，费用应纳入或显式追加制作预算，不可既免费聘任又重复扣费。
- 首套演出服：¥30,000 设计准备 + ¥25,000 × 实际成员数，九人 ¥255,000；服装不等于随录取立刻产生成品资产；完成交付后从在制成本转资产台账。
- 翻唱库首批 12 首虚构曲目；10 首单色、2 首双色仅为候选草案，不强迫配色均匀。莉奈建议初选六首（推荐组合 CV01/02/03/04/05/09，一年报价合计 ¥93,000），玩家可选更少或更多；**无六曲上限、无八曲硬门槛、无缺歌自动失败**。
- 翻唱授权为游戏架空的 `cover_arrangement_and_rehearsal_license` 一年期；不等同现实 JASRAC 年费。翻唱现场作品许可由场馆/主办/本团按演出合同负责；母带、录像、改编另行区分。不得对同一费用重复扣算。
- 歌曲原版人数仅作编排参考，不要求等人数；本团 Formation、关键 Part、歌曲熟练度由原设计自动训练/试排形成，成员离队、新入队需重新编排。

### 15.2 统一歌曲面板

三种共用 song_id 的视图：Card（封面、色块、Appeal、难度、原版人数）、List（密集选曲与费用）、Detail（固有八维 Palette、Appeal、技术难度、Theme、曲长、版权、Formation/Lead、实演版本与记录）。翻唱**额外**显示年度授权费、起止和剩余期限；原创显示 Making 状态、资产归属、投入和使用情况。`intrinsic_palette` 不跟随阵容变化；`presented_palette` 由实际演出决定。不得把训练熟练度、作品基本 Appeal 或最终 Impression 混为一个值。

### 15.3 时间与效果

2013 三月底起可以接翻唱商演；五月首次公开原创。出道拟定 8 曲，但曲目不足不阻塞：Staff 可安排重复曲、MC/互动或较短演出，改变整场 Impression 与满意度；不人为新增固定扣分项。只使用已经安排、取得授权、真正排练过的作品；允许未熟练作品上台但真实表现下降。

## 16. Team Strategy、Calendar 与训练政策

**只有会议变更策略**：初始 Team Strategy Meeting（训练、场次倾向、制作优先、视频/媒体、休息、外务优先级）后，Staff 根据策略和已承诺合同自动排程；玩家之后要调整策略须再次召集会议。日常时段冲突优先自动解，重要例外才 Inbox 阻塞。

训练档位：Low 2×2h/周、Medium 3×2h/周、High 4×3h/周；共同使用的排练室 ¥2,500/小时，对应**四周费用 ¥40k/¥60k/¥120k**（TUNABLE）。实际收费按租赁与取消规则执行、成员获得经验只按实际参与；疲劳与未成年限制先行。**不在 Chronicle 重写父游戏已经设计的歌曲 Familiarity 和主题熟练度公式。**

严格区分：原创编舞老师为项目外部制作／指导；三位创始成员负责开局审美、歌曲 Part、衣装概念和内部协调；没有额外常驻声乐/舞蹈教师开支。宮原的个人 Model=100 可带来指名杂志拍摄（例：单次 ¥30k 毛费，事务所留 50%，每月约一场是 TUNABLE，不保证；学业限制有效）。

## 17. 粉丝、特典会、媒体和 Live 经济

### 17.1 转化而非全知归因

- 初始 `Otaku=30`，**莉奈个人既有 20、宮原个人既有 10**；`Core=0`；初始 Public 参考莉奈 300／宮原 150（均为 TUNABLE 的认知量，不是稳定粉丝）。成员自带 Otaku 不等于每场都有 30 名本团动员。
- YouTube／小型电视／杂志外务增加 Public 可见度和**首次到 Live 的机会**，不自动等于 Core 或现金收入。序章不开放 CD 及额外物贩；Cheki 是允许的特典会收入，演出可否开特典取决于活动合同。
- 舞台 Impression 主要影响新客被吸引的概率；交流／Fan Engage 主导留存，舞台次之；长期重复到场与特典会表现决定 Otaku→Core 的聚合概率转化。
- 序章结尾 `Core/(Otaku+Core) ≈16%` 是成熟结构**参考锚点**，不可每个月机械强制到 16%；严格区分 Core 和 Otaku 的不重复人口，Cheki 张数与买家人数分开。
- 模型只使用聚合概率，不追踪单个粉丝的确定转化原因；任何 Reporter、Member Feedback、Weekly Review 都不能凭空写「N 人因歌声／YouTube 变 Core」。

### 17.2 定期公演与模拟验收

定期公演自 2013-12 获得机会；**早期几十人、2014 后期标准路线逐步接近满场**是待试玩的校准路径。`capacity=150` 为架空 JUKEBOX AKIBA 的 TUNABLE 游戏容量，不是现实历史容量。v0.4 财务情景期末标准参考约 Otaku 278／Core 53、现金 +¥1.37m；其它情景低动员可能负现金，需要借款/节流。上述结果是基于人为曝光、Cheki、合同收益假设的敏感性分析，非经过实测的真实转化估计。避免为对齐此数字而给粉丝设隐藏保底。

商演类型区分：有的现场只有固定出演费且不能办特典会；有的拼盘/定期演出允许 Cheki。演出时长、Slot、观众构成和许可由合同确定，不能一律有物贩或一律无特典。

## 18. 财务、借贷、资产与偶像估值

### 18.1 收支与风险

难度初始现金 `Easy ¥5m / Normal ¥3m / Hard ¥1.8m`（FROZEN_GAME_RULE）；合同初期三档见 §14；训练租赁见 §16。2013–2014 基本收入：Live、活动合同允许的 Cheki、偶尔个人 Model 外务；没有 CD／额外物贩；官方 YouTube 初期不算广告收入，小型 TV 默认不保底通告费。按实际完成活动才结算。

银行贷款是主动融资：可申请 ¥100k–¥3m，初始贷款本金总额上限 ¥3m；利率由**申请金额档 + 当前未偿本金档**确定。基础年息 3%；申请金额 >¥0.5m/+1%、>¥1m/+2%、>¥2m/+3%；存量债务 0/+0%，(0,¥0.5m]/+1%，(¥0.5m,¥1.5m]/+2%，>¥1.5m/+4%。每笔可选 12/24/36 月、固定息、等额本息；提前偿还无费用。额度与利率为 TUNABLE，审批不能依靠贷款循环创造无限授信。现金流对本金、利息、融资现金流分别记账。

### 18.2 资产台账与 Finance

- **资产负债表**：现金、已取得权利的原创歌曲净账面额、预付年度翻唱授权的剩余价值、取得条件满足时的练舞室使用权、服装设备；贷款、应付款以及适用租赁义务。
- **利润表**：收入和演出、排练、工资、外务等费用；已资本化可摊销项目只在适用条件下计提，不将制作预算直接等同本期损失或创造利润。
- **现金流量表**：经营、投资、融资现金流，贷款到账不算营业收入。
- **Asset Ledger**：歌曲、服装、设备和长租场地分别保留成本、合同/权利归属、可用状态、摊销/减值、实际使用、预计经营价值。按小时租练舞室通常只是租金费用；不是签一次小时合同就增加固定资产。
- **FM 式偶像身价**：可显示成员市场预估职业价值，随技能、粉丝、合同和外务变动；**绝不作为公司拥有的人身资产计入资产负债表**，也不是买卖身价/自动解约赔偿。
- Book Value、Estimated Value 分开；高估值不自动发现金或增加利润。原创歌曲只有取得可资本化权利才可确认为企业资产；未获权利的委托不得伪造所有权。

## 20. Live Report → Member Feedback → Weekly Review

1. `Live Report`：演出结束即时展示日期（JST）、场馆、可核验本团动员、收入、按成员 Cheki（若有）、定性现场反应、成员获得的实际经验；**不显示内部 Impression 原始值或未公开的粉丝真实转化参数**。
2. `Member Feedback`：偶像偶尔就其确实能观察或听到的信息发表**主观**短消息，例如「上次来的人又来排队」；不可在无问卷/身份追踪时假称掌握确切新增粉丝原因。没内容就不弹消息；不重复结算粉丝。
3. `Weekly Review`：主持 Leader 依事实账本概述当周趋势与可执行建议，不重播每场报告。首次出现机制时教学充分，之后按变化压缩。莉奈毕业后新生成报告必须用当时 Leader，历史报告保留旧作者。

即时反馈内容以可解释为目标，不改写后台概率：YouTube 和外务能提升首次到场机会，但 Staff 只能谨慎说「两者近期均上升」，不能确定指定数量的个人因果。

普通商演优先快速结算，第一次关键 Live 使用 `集合/入场→舞台关键段落→允许的特典会→结算` 的阶段化回顾；关键时期四次回顾为 **2013-05 出道、2013-12 定期开幕、2014-07 One-man、2014-08 TIF**。全部只从真实 Experience Ledger 选择证据，不额外奖励虚构新粉丝。

## 25. 中日英名词与粉丝术语边界（v0.8）

**必须固定**：`Public ≠ 新規`。Public 是模型中的团队级认知/关注人群层；新規是一次接触/到场/特典会行为的首次身份，属于事件或观测标签，并非粉丝层级。Otaku 首次买 Cheki 仍可能是新規特典会顾客，而拼盘中他团观众是本团计算的临时 Public，并不保证是真正首次接触本团。

默认不向玩家展示精确 Public/Otaku/Core 后台存量或具体个人转化原因；Live Report 提供可核实的票务、Cheki、收入事实，Member Feedback 是个人转述，Weekly Review 是趋势性解释。所有 UI、数据映射和三语翻译应遵循术语表。

**v0.8 修订记录**：新增完整三语术语索引和 Public / 新規 信息类型区分；既有 Live、Fan 和财务数值公式不变。
